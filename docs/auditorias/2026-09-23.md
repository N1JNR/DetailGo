## Detalhamento dos Achados

### 1. Endpoints de geocodificação sem autenticação Firebase (`geocode` e `reverseGeocode`)

- **Severidade:** MÉDIO
- **Arquivo afetado:** `functions/src/geo/geocode.ts`
- **Comportamento vulnerável:** As Cloud Functions HTTP `geocode` e `reverseGeocode` continuam públicas e não exigem nem verificam o cabeçalho `Authorization: Bearer <idToken>` de um usuário autenticado no Firebase.
- **Impacto possível:** Qualquer requisição HTTP externa não autenticada pode utilizar estas funções como proxy público para consultar a API do Google Maps Geocoding, consumindo a cota do projeto e gerando custos financeiros indesejados vinculados ao segredo `GOOGLE_GEOCODING_KEY`.
- **Correção recomendada:** Adicionar a verificação do Firebase ID Token (`admin.auth().verifyIdToken(idToken)`) no início das funções HTTP `geocode` e `reverseGeocode`, padrão já adotado em `createAsaasCheckout`.
- **Cabe teste de regressão:** Sim. Teste unitário garantindo que chamadas sem token válido ou com token inválido retornem status `401 Unauthorized`.

---

### 2. Ausência de validação de limites nos parâmetros do proxy `reverseGeocode`

- **Severidade:** BAIXO
- **Arquivo afetado:** `functions/src/geo/geocode.ts` (linhas 72–78)
- **Comportamento vulnerável:** A função `reverseGeocode` verifica apenas se `lat` e `lng` não são nulos/indefinidos, mas não valida se pertencem ao tipo `number` dentro dos intervalos geográficos aceitos (`-90 <= lat <= 90` e `-180 <= lng <= 180`).
- **Impacto possível:** O envio de valores não numéricos ou coordenadas fora do intervalo geográfico válido causa erros na API externa do Google Maps ou comportamento indeterminado na extração do endereço.
- **Correção recomendada:** Incluir validações explícitas do tipo `typeof lat === 'number'` e checagem de limites numéricos para `lat` e `lng`.
- **Cabe teste de regressão:** Sim. Teste unitário garantindo que valores inválidos retornem status `400 Bad Request`.

## Verificação das Demais Superfícies de Segurança

### A. Credenciais e Histórico do Git

- **Status:** **CONFORME (BAIXO / Sem achados)**
- **Análise:** Varredura no código fonte e no histórico recente do Git confirma ausência de segredos ou chaves privadas commitados. As credenciais (`ASAAS_API_KEY`, `ASAAS_WEBHOOK_TOKEN`, `GOOGLE_GEOCODING_KEY`) utilizam o recurso `defineSecret` do Firebase Secret Manager.

### B. Logs e Proteção de Dados Sensíveis (PII)

- **Status:** **CONFORME (BAIXO / Sem achados)**
- **Análise:** Não foram encontrados comandos `console.log` na aplicação (`src/`) nem em `functions/src/`. As Cloud Functions usam `logger` registrando estritamente IDs opacos (`shopId`, `paymentId`, `checkoutSession`), preservando a privacidade de e-mails, telefones, senhas e tokens FCM.

### C. Regras do Firestore e Storage

- **Status:** **CONFORME (BAIXO / Sem achados)**
- **Análise:** O isolamento multi-tenant no Firestore é rigoroso: todas as subcoleções sob `shops/{shopId}` dependem de checagem do dono (`isShopOwner`) para escrita ou escopo restrito. A regra em `users/{userId}` impede alteração do campo `role`, prevenindo escalação de privilégios. As regras em `storage.rules` restringem uploads para `users/{uid}/` limitados a 5 MB e tipo imagem.

### D. Webhooks e Pagamentos (Asaas)

- **Status:** **CONFORME (BAIXO / Sem achados)**
- **Análise:** A função `asaasWebhook` valida o cabeçalho `asaas-access-token` via comparador de tempo constante (`timingSafeEqual`). Ativações de assinatura ocorrem transacionalmente no backend Firestore via Cloud Functions; o aplicativo cliente não possui capacidade de alterar estados de pagamento ou assinatura.

---

## Recomendação Geral

Recomenda-se planejar a implementação da autenticação por Firebase ID Token nos endpoints `geocode` e `reverseGeocode` em `functions/src/geo/geocode.ts`, sanando a única pendência de severidade média em aberto na plataforma.
