# Relatório de Auditoria de Segurança — 2026-11-04

**Data da execução:** 04/11/2026
**Escopo:** Aplicação mobile (React Native 0.81 / React 19), regras de autorização do Firestore (`firestore.rules`) e Storage (`storage.rules`), Cloud Functions v2 em Node.js (`functions/src/`), autenticação Firebase, fluxos de assinatura/cobrança Asaas, isolamento multi-tenant e segurança em dependências.

## O que mudou desde a última auditoria (2026-10-14)

Comparação com o relatório anterior (`docs/auditorias/2026-10-14.md`):

- **[CORRIGIDO] Vínculo de assinatura movido para subcoleção restrita (`shopBilling`) (ALTO):**
  No commit `e0a00de`, o vínculo com a assinatura do Asaas (`asaasSubscriptionId`), anteriormente armazenado em `shops/{shopId}`, foi migrado para a coleção isolada `/shopBilling/{shopId}`. O `firestore.rules` fecha `/shopBilling/{shopId}` para leitura e escrita por clientes (`allow read, write: if false;`), permitindo acesso apenas ao Admin SDK das Cloud Functions. A autorização do cancelamento em `asaasSubscription.ts` agora lê diretamente de `shopBilling`, prevenindo que um dono informe o ID de assinatura de outro estabelecimento e cancele o serviço alheio.
- **[CORRIGIDO] Leitura pública de documentos de lojas restrita a usuários autenticados (MÉDIO):**
  Em `firestore.rules`, a permissão de leitura de `shops/{shopId}` foi alterada de `allow read: if true;` para `allow read: if isSignedIn();`. Isso impede que requisições não autenticadas leiam os dados da estética, uma vez que as regras do Firestore não oferecem controle em nível de campo.
- **[CORRIGIDO] Proteção contra adulteração de planos pagos e trial perpétuo (MÉDIO):**
  Em `firestore.rules`, a função `camposDeCobranca()` bloqueia atualizações pelo cliente dos campos `ownerId`, `subscriptionStatus`, `activeUntil`, `trialEndsAt`, `asaasSubscriptionId`, `lastPaymentId` e `lastPaymentAt`. Além disso, a função `trialDeNascimentoValido()` impõe teto de 8 dias ao `trialEndsAt` no cadastro, impedindo que um usuário crie um shop com trial vitalício em 2099.
- **[CORRIGIDO] Validação de caminho contra injeção em `shopId` (MÉDIO):**
  Em `shopBilling.ts` e `shopOwnerGuard.ts`, o `shopId` é explicitamente validado (`/^[a-zA-Z0-9_-]+$/`), prevenindo que caminhos com barras (`/`) alcancem subcoleções não autorizadas.
- **[EM ABERTO / DÉBITO] Proxies de geocodificação sem autenticação Firebase (`geocode` e `reverseGeocode`) (MÉDIO):**
  Permanece sem exigência de Firebase ID Token no cabeçalho das requisições HTTP em `functions/src/geo/geocode.ts`. A mitigação ativa continua utilizando limitação de taxa por IP com janela diária (`functions/src/geo/limitePorIp.ts`), mantida por decisão de design para viabilizar busca de endereço no onboarding antes da criação da conta.

## Detalhamento dos Achados

### 1. Endpoints de geocodificação sem autenticação Firebase (`geocode` e `reverseGeocode`)

- **Severidade:** MÉDIO
- **Arquivo afetado:** `functions/src/geo/geocode.ts`
- **Comportamento vulnerável:** As Cloud Functions HTTP `geocode` e `reverseGeocode` permanecem expostas publicamente e não exigem nem validam o cabeçalho `Authorization: Bearer <idToken>` de um usuário logado no Firebase.
- **Impacto possível:** Requisições automatizadas ou usuários mal-intencionados podem utilizar estas funções como proxy anônimo para o Google Maps Geocoding API, gerando custos financeiros indesejados vinculados ao segredo `GOOGLE_GEOCODING_KEY`, caso ultrapassem ou rotacionem endereços IP para contornar a taxa de 40 chamadas/dia por IP.
- **Correção recomendada:** Caso o fluxo de onboarding permita login anônimo ou cadastro prévio antes da definição da localização da estética, adicionar a validação do Firebase ID Token (`admin.auth().verifyIdToken(idToken)`), nos mesmos moldes implementados em `createAsaasCheckout`.
- **Cabe teste de regressão:** Sim. Teste unitário certificando que requisições HTTP sem token de autorização ou com token inválido recebam status `401 Unauthorized`.

## Verificação das Demais Superfícies de Segurança

### A. Credenciais e Histórico do Git

- **Status:** **CONFORME (BAIXO / Sem achados)**
- **Análise:** Varredura detalhada no código-fonte (`src/`, `functions/src/`, arquivos de configuração) e no histórico recente do Git não revelou nenhuma credencial, segredo ou chave privada exposta.
- O `.gitignore` cobre rigorosamente `.env*`, `*.key`, `*.pem`, `secrets/` e arquivos de credenciais do Firebase (`google-services.json`).
- As Cloud Functions utilizam o `defineSecret` do Firebase Secret Manager (`ASAAS_API_KEY`, `ASAAS_WEBHOOK_TOKEN`, `GOOGLE_GEOCODING_KEY`).

### B. Logs e Proteção de Dados Sensíveis (PII)

- **Status:** **CONFORME (BAIXO / Sem achados)**
- **Análise:** Nenhum comando `console.log` foi identificado em `src/` ou `functions/src/`.
- As mensagens emitidas via `logger` em Cloud Functions e serviços compartilham exclusivamente identificadores opacos (`shopId`, `paymentId`, `customerUid`), sem exibir dados pessoais identificáveis (PII) como nomes, telefones, e-mails, tokens FCM ou payloads completos de faturamento.

### C. Regras do Firestore e Storage

- **Status:** **CONFORME (BAIXO / Sem achados)**
- **Análise:**
  - `firestore.rules` foi validado contra a suíte completa de 60 testes no Firebase Emulator (`npm run test:rules`).
  - Documentos `shops/{shopId}` exigem autenticação para leitura e barram escrita nos campos de faturamento (`camposDeCobranca()`).
  - A coleção `/shopBilling/{shopId}` está estritamente fechada (`allow read, write: if false;`).
  - A modificação do campo `role` em `users/{userId}` é bloqueada por regras do Firestore (`!diff.affectedKeys().hasAny(['role'])`).
  - `storage.rules` restringe gravações estritamente aos caminhos `users/{uid}/...` com validação de tipo MIME de imagem (`image/.*`) e teto de tamanho de arquivo de 5 MB.

### D. Webhooks e Pagamentos (Asaas/MercadoPago)

- **Status:** **CONFORME (BAIXO / Sem achados)**
- **Análise:** O endpoint `asaasWebhook` valida o cabeçalho `asaas-access-token` utilizando o comparador em tempo constante `timingSafeEqual` (`functions/src/payment/asaasWebhookToken.ts`), mitigando vulnerabilidades de timing attacks. O processamento das assinaturas e a ativação de planos ocorrem atomicamente no backend. O aplicativo cliente não tem privilégio de confirmar pagamentos ou alterar estados de cobrança.

### E. Escalação de Papel (`customer` virando `owner`)

- **Status:** **CONFORME (BAIXO / Sem achados)**
- **Análise:** A regra `allow update` de `users/{userId}` impede a alteração da chave `role` após a criação inicial do documento de perfil. Testes automatizados no emulador cobrem e confirmam o bloqueio de auto-promoção de `customer` para `owner`.

### F. Travessia Entre Tenants (Multi-Tenant)

- **Status:** **CONFORME (BAIXO / Sem achados)**
- **Análise:** Todas as consultas no aplicativo e serviços têm escopo restrito a `shopId`. Acesso a agendamentos, serviços e configurações de um shop por clientes ou donos de outras estéticas é estritamente impedido por regras no Firestore e no frontend.

### G. Validação de Entrada

- **Status:** **CONFORME (BAIXO / Sem achados)**
- **Análise:** Formulários do aplicativo passam pelos utilitários de validação (`src/shared/utils/validation.utils.ts` e `cep.utils.ts`). No backend, os dados de entrada das funções passam por validações rígidas de tipos e formatos (`validarEndereco`, `validarCoordenadas` e validação regex de `shopId`).

### H. Armazenamento Local Inseguro

- **Status:** **CONFORME (BAIXO / Sem achados)**
- **Análise:** O `AsyncStorage` armazena exclusivamente configurações visuais e preferências de UI da sessão (tema, seleção temporária de shop). Nenhuma credencial de autenticação, token de cartão ou segredo é armazenado em texto claro no armazenamento local.

### I. Riscos Aceitos e Dependências

- **Status:** **MONITORADO (Conforme memory-security.md)**
  - O paywall é validado no cliente; as regras do Firestore protegem a integridade e propriedade dos dados via `isShopOwner(shopId)`, mas a cobrança em si não barra o agendamento no Firestore.
  - Vulnerabilidades em ferramentas de desenvolvimento (`node-forge`, `braces`, `image-size`) são mantidas como riscos aceitos documentados devido a restrições upstream e compatibilidade do Metro com React Native 0.81.
  - App Check permanece planejado para ser habilitado após o primeiro upload e obtenção da SHA-1 na Play Console.

## Recomendação Geral

Priorizar a introdução de autenticação nos proxies de geocodificação (`geocode` e `reverseGeocode`) caso haja ajuste no fluxo de onboarding, encerrando o único apontamento de risco médio contínuo do projeto.
